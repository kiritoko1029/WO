## 三个新功能实现方案

### 功能 1：静音/调整其他人语音音量

**方案 A：`audio.volume` + `audio.muted`**（改动最小）

数据流：`RTCPeerConnection.ontrack` → `attachRemoteTrack` → `AudioOutput.attach(track)` → `<audio>` 元素播放。

**改动：**
- `audio-output.ts`：`AudioElementLike` 接口加 `volume: number`；`AudioOutput` 接口加 `setVolume(volume: number): void`；实现里 `element.volume = volume`
- `voice-controller.ts`：加 `remoteVolume` 字段 + `setRemoteVolume(volume): void`
- `call-store.tsx`：`CallSnapshot` 加 `remoteVolume: number`（0-1，默认 1）；`CallController` 加 `setRemoteVolume(volume): Promise<void>`；passive stub
- `CallToolbar.tsx`：设置弹窗里扬声器选择下方加音量滑块 `<input type="range" min="0" max="1" step="0.05">`；当 volume=0 时等价于静音
- `RoomRoute.tsx`：绑定 `remoteVolume` + `onRemoteVolumeChange`

**关于"静音"语义**：双人通话中只有一个远端参与者，所以"静音对方"="扬声器静音"。现有的 `outputMuted` 就是全局扬声器静音。我新增的 `remoteVolume` 滑块覆盖了这个需求——拖到 0 就静音。保留现有 `outputMuted` 按钮不变（快速静音切换），音量滑块作为精细控制。

### 功能 2：共享本机桌面音频（macOS 系统 picker）

这个功能需要打通 4 层防线。核心改动是让屏幕共享支持同时采集音频轨道。

**改动点：**

#### 2.1 renderer 采集约束 + 轨道校验
- `screen-controller.ts`：`DISPLAY_CAPTURE_CONSTRAINTS` 改为 `audio: true`
- `startSelectedCapture` 的轨道校验放宽：允许 0-1 个 audio track + 1 个 video track
- 新增 audio track 的 sender 绑定逻辑（用 peer 的 audio transceiver sender 或新建 sender）

#### 2.2 main 进程 display capture 策略
- `capture-policy.ts`：`isDisplayCaptureRequestAllowed` 去掉 `!audioRequested` 条件，允许 audio

#### 2.3 main 进程 picker 回调
- `capture-sources.ts`：`DisplayMediaSession` 回调类型加 `audio?: 'loopback'`；callback 提供 audio
- **关键架构决策**：切换到 `useSystemPicker: true`（macOS 系统弹窗），因为 macOS 的 loopback audio 只在系统 picker 下可用。保留自定义 picker 作为 fallback（不要求音频时）

#### 2.4 main 进程 media 权限
- `window-security.ts`：`setPermissionRequestHandler` 和 `setPermissionCheckHandler` 增加 display-capture + audio 的组合放行

#### 2.5 screen-controller 传 audio 到 sender
- 当前 screen-controller 只处理 video track（`queueSenderTrack`）。需要把 audio track 也通过 `replaceTrack` 发送。
- **关键**：WebRTC peer connection 的 audio transceiver 当前用于麦克风。共享桌面音频需要**另一个 audio sender**，或者把桌面音频混入麦克风轨道（不推荐，会丢失独立控制）。
- **方案**：在 transceiver-plan 新增一个 audio transceiver 专门用于桌面音频，或者用 `addTrack` 动态添加。考虑到 SDP 协商复杂性，**最简方案**是：共享桌面音频时，用一个新的 transceiver（`pc.addTrack(audioTrack)`），触发重协商。

**实际上更简单的方案**：把桌面音频和麦克风的音频**合并**到同一个 sender。用 Web Audio API 创建一个混合节点（麦克风 + 桌面音频 → MediaStreamDestination → 替换 audio sender track）。但这会让降噪处理链变复杂。

**最终决策**：先做**最简路径**——共享桌面音频时，新增一个 audio transceiver。这需要修改 transceiver-plan 和协商逻辑，改动量较大但架构最干净。

### 功能 3 实施顺序

由于三个功能复杂度差异大，建议分步实施：
1. **先做功能 1（静音+音量）**：改动最小，独立，可快速完成验证
2. **再做功能 2（桌面音频）**：复杂度高，涉及 main/renderer/transceiver 多层

### 文件改动清单

**功能 1（静音+音量）：**
1. `audio-output.ts` — 加 `volume` / `setVolume`
2. `voice-controller.ts` — 加 `remoteVolume` / `setRemoteVolume`
3. `call-store.tsx` — CallSnapshot 加 `remoteVolume`，CallController 加 `setRemoteVolume`
4. `CallToolbar.tsx` — 设置弹窗加音量滑块
5. `RoomRoute.tsx` — 绑定 props
6. 测试更新

**功能 2（桌面音频）：**
7. `screen-controller.ts` — 采集约束 audio:true + 轨道校验放宽 + audio sender
8. `capture-policy.ts` — 允许 audioRequested
9. `capture-sources.ts` — 系统 picker + loopback audio callback
10. `window-security.ts` — 权限组合放行
11. `transceiver-plan.ts` — 新增桌面音频 transceiver（或 addTrack 动态添加）
12. `call-store.tsx` — screen share 时处理 audio track
13. 测试更新

## 不做的事情
- 不做 web 端的桌面音频共享（web 端 capture API 架构不同，后续单独处理）
- 不做桌面音频的独立音量控制（混入主音频流）
- 不改变现有麦克风降噪链
